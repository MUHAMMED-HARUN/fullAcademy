# التخطيط الصارم لتحسين الميزات متعددة الخدمات (Strict Read-Only Planner)

استخدم هذه المهارة عندما يطلب المستخدم "خطة" أو "تحليل لتنفيذ ميزة تضم عدة خدمات" قبل البدء بكتابة أو تعديل الكود.

## 1. القيود الحمراء (ممنوع تجاوزها مطلقاً)

- **حظر كامل لأدوات التعديل (Zero-Write Policy):** أثناء مرحلة التخطيط، يُمنع منعاً باتاً استدعاء أي أداة لإنشاء أو تعديل أو حذف الملفات، أو تشغيل أوامر تغير حالة المشروع. المسموح فقط هو أدوات القراءة والبحث (`read` / `glob` / `grep`).
- **منع التعميم:** يُمنع كتابة خطط إنشائية عامة (مثل "سنحسن الـ Validator والـ Mapper"). يجب ذكر أسماء الملفات، الكلاسات، الـ Endpoints، والحقول المتأثرة بالاسم الدقيق.
- **أولوية توجيهات المستخدم:** أي شرط أو توجيه خاص يذكره المستخدم في رسالته له الأولوية القصوى، ويجب توضيح كيف سيُطبق في الخدمة المعنية.
- **مراجعة الأمان والنطاق:** راجع مهارة `backend-security-scoping` إلزامياً عند التخطيط لتضمين دورة الصلاحيات ونطاق ملكية البيانات، مع الالتزام بقيود القراءة فقط لهذه المهارة.
- **بوابة التنفيذ المتدرج (One-Service-Per-Turn Gate):** الخطة تُبنى للميزة كاملة، لكن عند بدء التنفيذ لاحقاً، يُنفذ **خدمة فرعية واحدة فقط (Backend + Frontend Logic + UI)** في كل مرحلة، ويُمنع الانتقال للخدمة التالية قبل مراجعة المستخدم ونجاح `dotnet build` و `ESLint`[cite: 5].

## 2. خطوات الفحص وبناء الخطة

1. **مسح الكود الفعلي للخدمات:** اقرأ ملفات جميع الخدمات الفرعية التابعة للميزة في الطبقات الخمس (`Domain`, `Application`, `Infrastructure`, `WebApi`, `Frontend`)[cite: 5].
2. **رسم شجرة الاعتماديات (Dependency Graph):** حدد أي خدمة تعتمد على خدمة أخرى في العلاقات أو شاشات `Upsert` / `Lookup`، ورتّب التنفيذ من **الخدمة المستقلة (رقم 1)** إلى **الخدمة المركبة التابعة (الأخيرة)**.
3. **فحص العقود ونمط الاختيار لكل خدمة:**
   - حدد هل تحتاج الخدمة إلى `GetListFilter` مدعوم بـ `GridifyAsync` و `BaseFilterQuery<T>` (بدون `IgnoreQueryFilters()`).
   - حدد هل تحتاج شاشة التعديل إلى Endpoint مخصص `get-for-upsert` لإرجاع المعرّفات الكاملة.
   - حدد نمط الاختيار الدقيق لكل حقل علاقة في الواجهة وفق مهارة `frontend-selection-patterns`:
     - `Standard Select` (للقيم الثابتة القليلة والـ Enums).
     - `Nested Combo` (للعلاقات الهرمية المتدرجة مع تصفير الأبناء عند تغيير الأب).
     - `GenericSearchByFilter` (للكيانات الكبيرة عبر Gridify بصيغة `Field=*Value` حصراً دون `*` في النهاية، مع تزامن `ID` + `Name` + `Card`).

## 3. القالب الإلزامي لمخرجات الخطة في المحادثة

اعرض الخطة للمستخدم مقسمة بوضوح كالتالي:

### أولاً: ترتيب تنفيذ الخدمات (Dependency Order)
قائمة مرقمة بالخدمات من (1) إلى (N) مع سبب ترتيب كل خدمة في موقعها.

### ثانياً: بطاقة الخطة التفصيلية لكل خدمة (Service-by-Service Cards)
لكل خدمة بالترتيب، اذكر النقاط الخمس التالية بدقة:
1. **العيوب المكتشفة حالياً:** (Namespaces، أخطاء الـ Handlers/Repos، فجوات الـ DTOs، تعارض أسماء الحقول بين Backend و Frontend، مشاكل الـ UI)[cite: 5].
2. **خطة الـ Backend:** الملفات والـ Endpoints والـ Queries/Commands والـ Validators التي ستُنشأ أو تُعدّل بالاسم[cite: 5].
3. **خطة منطق الـ Frontend:** تعديلات `Repository`, `Mapper`, `Zod Schema`, `Service`, `Pinia Store`[cite: 5].
4. **خطة الـ UI/UX ونمط الاختيار:** تعديلات `View`, `List`, `Card`, `Upsert`، وتحديد نمط الاختيار لكل حقل علاقة وكيفية تهيئته في وضع `Edit Mode`[cite: 5].
5. **تطبيق توجيهات المستخدم الخاصة:** كيف تم إسقاط شروط المستخدم على هذه الخدمة.

## 4. شرط التوقف الإلزامي
بعد طباعة الخطة في المحادثة، **توقف تماماً عن العمل** واطلب من المستخدم مراجعة الخطة وإعطاء الإشارة للبدء بتنفيذ **الخدمة رقم (1) فقط**.
