# التخطيط الصارم لتحسين الميزات متعددة الخدمات (Strict Read-Only Planner)

استخدم هذه المهارة عندما يطلب المستخدم "خطة" أو "تحليل لتنفيذ ميزة تضم عدة خدمات" قبل البدء بكتابة أو تعديل الكود.

## 1. القيود الحمراء (ممنوع تجاوزها مطلقاً)

- **حظر كامل لتعديل الأكواد البرمجية (Zero-Code-Write Policy):** أثناء مرحلة التخطيط، يُمنع منعاً باتاً إنشاء، تعديل، أو حذف أي ملف كود برمجية تابعة للنظام (Backend/Frontend)، أو تشغيل أوامر برمجية تغير حالة المشروع. الأدوات المصرح بها فقط هي أدوات القراءة والبحث (`read` / `glob` / `grep`).
- **استثناء كتابة الخطة التوثيقية (Documentation-Only Write Exception):** 
  - يُسمح حصراً بكتابة وتفريغ مخرجات الخطة في ملفات Markdown داخل مسار التوثيق التالي فقط:
    `./.opencode/Plans/[اسم-الميزة-أو-الطلب]/`
  - يُمنع إنشاء أو تعديل أي ملفات خارج مجلد `.opencode/Plans/`.
- **نمط تسمية ملفات التخطيط:**
  - لكل أمر تخطيط، يُنشأ مجلد مستقل للميزة تحت: `.opencode/Plans/<Feature-Name>/`
  - لكل خدمة مشمولة، يُنشأ ملف خطة مستقل يُسمى بصيغة:
    `[Priority]_[ServiceName].md` (مثال: `01_AcademicYear.md`, `02_GradeLevel.md`).
- **منع التعميم:** يُمنع كتابة خطط إنشائية عامة (مثل "سنحسن الـ Validator والـ Mapper"). يجب ذكر أسماء الملفات، الكلاسات، الـ Endpoints، والحقول المتأثرة بالاسم الدقيق.
- **أولوية توجيهات المستخدم:** أي شرط أو توجيه خاص يذكره المستخدم في رسالته له الأولوية القصوى، ويجب توضيح كيف سيُطبق في الخدمة المعنية.
- **مراجعة الأمان والنطاق:** راجع مهارة `backend-security-scoping` إلزامياً عند التخطيط لتضمين دورة الصلاحيات ونطاق ملكية البيانات.
- **بوابة التنفيذ المتدرج (One-Service-Per-Turn Gate):** الخطة تُبنى للميزة كاملة وتُفرّغ في الملفات المخصصة، ولكن عند بدء التنفيذ الفعلي لاحقاً، يُنفذ **خدمة فرعية واحدة فقط (Backend + Frontend Logic + UI)** في كل مرحلة، ويُمنع الانتقال للخدمة التالية قبل مراجعة المستخدم ونجاح الفحوصات الأساسية (`dotnet build` و `ESLint`).

## 2. خطوات الفحص وبناء الخطة

1. **مسح الكود الفعلي للخدمات:** اقرأ ملفات جميع الخدمات الفرعية التابعة للميزة في الطبقات الخمس (`Domain`, `Application`, `Infrastructure`, `WebApi`, `Frontend`).
2. **رسم شجرة الاعتماديات (Dependency Graph):** حدد أي خدمة تعتمد على خدمة أخرى في العلاقات أو شاشات `Upsert` / `Lookup`، ورتّب أولوية التنفيذ من **الخدمة المستقلة (رقم 01)** إلى **الخدمة المركبة التابعة (الأخيرة)**.
3. **فحص العقود ونمط الاختيار لكل خدمة:**
   - حدد هل تحتاج الخدمة إلى `GetListFilter` مدعوم بـ `GridifyAsync` و `BaseFilterQuery<T>` (بدون `IgnoreQueryFilters()`).
   - حدد هل تحتاج شاشة التعديل إلى Endpoint مخصص `get-for-upsert` لإرجاع المعرّفات الكاملة.
   - حدد نمط الاختيار الدقيق لكل حقل علاقة في الواجهة وفق مهارة `frontend-selection-patterns`:
     - `Standard Select` (للقيم الثابتة والـ Enums).
     - `Nested Combo` (للعلاقات الهرمية المتدرجة مع تصفير الأبناء عند تغيير الأب).
     - `GenericSearchByFilter` (للكيانات الكبيرة عبر Gridify بصيغة `Field=*Value` حصراً دون `*` في النهاية، مع تزامن `ID` + `Name` + `Card`).

## 3. تفريغ الخطة وقالب المخرجات

يتم تفريغ الخطة لكل خدمة داخل ملفها الخاص في المسار المحدد:
`.opencode/Plans/[Feature-Name]/[Priority]_[ServiceName].md`

ويحتوي كل ملف خدمة على النقاط الخمس التالية بدقة:
1. **العيوب المكتشفة حالياً:** (Namespaces، أخطاء الـ Handlers/Repos، فجوات الـ DTOs، تعارض أسماء الحقول بين Backend و Frontend، مشاكل الـ UI).
2. **خطة الـ Backend:** الملفات والـ Endpoints والـ Queries/Commands والـ Validators التي ستُنشأ أو تُعدّل بالاسم الدقيق.
3. **خطة منطق الـ Frontend:** تعديلات `Repository`, `Mapper`, `Zod Schema`, `Service`, `Pinia Store`.
4. **خطة الـ UI/UX ونمط الاختيار:** تعديلات `View`, `List`, `Card`, `Upsert`، وتحديد نمط الاختيار لكل حقل علاقة وكيفية تهيئته في وضع `Edit Mode`.
5. **تطبيق توجيهات المستخدم الخاصة:** كيف تم إسقاط شروط وتفضيلات المستخدم على هذه الخدمة بعينها.

بالإضافة لذلك، يُعرض ملخص سريع في المحادثة يوضح:
- قائمة ترتيب الاعتماديات والأولويات (1 إلى N).
- مسارات الملفات التي تم إنشاؤها داخل مجلد `.opencode/Plans/`.

## 4. شرط التوقف الإلزامي
بعد تفريغ ملفات الخطة وطباعة ملخص الترتيب في المحادثة، **توقف تماماً عن العمل** واطلب من المستخدم مراجعة الخطة وإعطاء الإشارة للبدء بتنفيذ **الخدمة رقم (01) فقط**.
